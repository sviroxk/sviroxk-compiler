# AGENTS.md — правила для ИИ-агентов и людей

Этот файл главнее остальных документов, когда речь о процессе. Читать целиком перед работой.

## Сборка и тесты

```bash
CXX=clang++ CXXFLAGS="-Wall -Wextra -Werror" ./build.sh   # нужен только llvm-config (LLVM 18–23)
./test.sh                                                  # все тесты; код 0 = всё прошло
./test-conformance.sh
```

- Сборка остаётся `./build.sh` + `llvm-config`, без CMake и новых зависимостей.
- Код компилятора — C++20 (`build.sh` задаёт `-std=c++20` поверх флагов `llvm-config`). Новый код пишется на C++20.
- Основная версия LLVM — 23.1.5: на ней разработка и обязательная локальная проверка каждого PR (сборка `-Wall -Wextra -Werror`, `./test.sh`, `./test-conformance.sh`, ASan/UBSan). 18–22 поддерживаются (различия API — через `#if LLVM_VERSION_MAJOR`, не удалять), их проверяет CI-матрица. Локально каждый PR проверяется минимум на 23.1.5 (и на 18.1.8, если правка может зависеть от версии). В описании PR писать, на каких версиях проверено.
- Ветка `main` защищена: обязательная проверка называется `build-and-test`. Любая правка CI-файла обязана сохранять задачу с этим именем (итоговую поверх матрицы). Защиту не обходить (`--admin`, смена правил).
- CI (`.github/workflows/ci.yml`, PR #49): задача-матрица `llvm` — LLVM 18–23 (ASan/UBSan на 23 и 18), итоговая `build-and-test` зелёная, только если прошла вся матрица. Агент не может менять `.github/workflows/*`: новый шаг проверки добавлять в `test.sh` или передавать текст файла владельцу.
- Перед слиянием ветка `dev` должна быть актуальна относительно `main` (так требует защита).
- Каждый ручной запуск компилятора — только с таймаутом: `timeout 10 ./sc file.svx > out.ll`. Зависание = баг компилятора, а не повод ждать дольше.
- Запуск программы: `./sc file.svx > out.ll && lli out.ll`.

## Как работать

1. Одна задача = один PR `dev` → `main`. В репозитории ровно две ветки: `main` и постоянная рабочая `dev`; перед новой задачей `dev` должна быть выровнена по свежему `main`.
2. PR до ~300 изменённых строк. Больше — разбить.
3. В описании PR два раздела: **Что сделано** и **Как проверено** (команды и реальные числа: сколько тестов, что упало до правки).
4. Squash-слияние выполнять без удаления `dev`. После слияния выровнять `dev` по свежему `main` через `--force-with-lease`, проверив ожидаемый remote head; не накапливать merge-коммиты и старые коммиты PR.
5. В `main` напрямую не пушить. По постоянному разрешению владельца агент может squash-слить PR только после полностью зелёного CI и всех тестов; затем проверить CI `main`. При красном CI или сомнениях не сливать, сообщить владельцу.
6. Каждый исправленный баг = тест, который падал до исправления и проходит после.
7. Каждая новая возможность = положительный тест с проверкой вывода и отрицательный тест с проверкой текста ошибки.
8. Готовность считается по тестам, а не по процентам. Не писать «100%», «всё готово» без теста, который это показывает.
9. Если тест упирается в баг вне задачи — не чинить попутно, записать в описание PR.

## Каким документам верить

- Что сделано и что делать дальше (очередь работ для следующего агента) — `docs/handoff.md`. Закрыл задачу — поправь очередь в том же PR.
- Правда — это код и `test.sh`. Журнал работы — `docs/progress.md` (дописывать в конец, коротко).
- Язык описывает только `docs/spec.md`. Каждый пример в нём проверяется `tests/spec-examples.sh` (запускается из `test.sh`). Изменил поведение — поправь спецификацию и её пример в том же PR.
- Новые примеры и тесты пишутся только новыми словами (`fn`, `print`, `int` …); старые синонимы удалены (spec §16).
- `docs/core-audit.md` — стратегический план владельца, не описание языка: синтаксиса из него в компиляторе может не быть.
- Перед тем как опираться на пример синтаксиса из документа, скомпилируй его.
