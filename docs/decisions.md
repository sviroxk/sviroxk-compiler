# Технические решения SC

## D-001. Синтаксис стандартной библиотеки и namespace imports

**Статус:** временное решение, текущая реализация.

**Варианты:**
1. Ввести сразу `use math` и квалифицированные `math.abs`.
2. Использовать относительный `import "path/file.svx"` и именованные функции с префиксом модуля.

**Выбор:** вариант 2 до появления per-module AST/symbol tables. Сейчас `import` рекурсивно склеивает токены в общий compilation unit, поэтому `use`/qualified lookup потребовали бы поверхностной подстановки имён и создали бы конфликты. Путь и API явно отражают реальное поведение: `stdlib/math/math.svx`, `math_abs(...)`.

**Последствия:** старый синтаксис сохраняется; namespace call syntax отложен до реализации symbol resolution. Не документировать `use math` как поддерживаемый API.

## D-002. Возврат результата `replace`

**Статус:** заменено D-014 (2026-11-13).

**Выбор:** `replace(source, needle, replacement)` заменяет первое вхождение, выделяет новый `ptr`; вызывающий обязан вызвать `del`. На allocation failure/size overflow backend сейчас завершает процесс через `abort`.

**Причина:** в текущем языке нет string-with-length и Result/OOM error contract. Fixed-size stack buffer был небезопасен; heap result без скрытого владения хотя бы имеет явный release.

**Риски/следующий шаг:** утечки возможны при забытом `del`; recoverable allocation error и owning string откладываются до общей модели ресурсов.

## D-003. Логические операторы

**Статус:** LLVM short-circuit CFG.

`&&` и `||` генерируются как условный переход с merge/PHI, чтобы не вычислять правый операнд без необходимости. Проверяется side-effect regression. Сейчас условия принимают bool и integer truthy/falsy; строгая bool-only policy отложена.

## D-004. Bounds checks

**Статус:** runtime check только для статических массивов.

Индекс проверяется перед inbounds GEP; ошибка печатает source line/column и завершает программу ненулевым кодом. Dynamic `ptr` arrays не хранят length, поэтому безопасная проверка невозможна без descriptor/allocator redesign.


## D-005. Перенос структур по значению из PR22 (шаг 4б)

**Источник поведения:** закрытый PR22 `edcaacf`, stage 5 `5cfce47`.
Параметр `Name value` — aggregate copy в локальный слот функции; скалярные
и вложенные value-поля независимы от исходной переменной. `Inner field`
добавлен как историческая запись типа вложенного поля; bare `Inner field` сохранён.
Типы структур регистрируются до LLVM function signatures, параметр получает
metadata для lookup полей. Существующий load aggregate переменной уже подходит
для аргумента, поэтому лишняя временная materialization из PR22 не требуется.
Это не ownership ABI: pointer-поля копируют адрес, не выделение; clone/move,
struct returns, `defer`/`drop` не входят в шаг. Новых решений о памяти не принято.


## D-006. Безопасное подмножество `defer` при переносе PR22

Источник синтаксиса и scope-exit/LIFO поведения — PR22, `fa7e9ce`.
Вместо разрушаемого общего stack используется генерация cleanup для каждого
пути CFG: ранний return одной ветки не удаляет cleanup другой. Регистрация
запоминает lexical bindings, но не значения; return expression вычисляется
после cleanup, как в историческом lowering. Break/continue выполняют cleanup
покидаемых областей, не внешней функции.

Принято временное ограничение первого шага: только обычная операция/вызов.
`defer return/break/continue`, объявления, вложенные defer и control-flow
отклоняются понятной semantic-ошибкой. PR22 принимал их синтаксически, но не
задавал корректного поведения (например, двойной return в IR); этот баг не
переносится. Ограничение можно расширить по решению владельца. `drop` отдельно.

## D-009. Математические функции от целых (2026-11-12)

Решение владельца («как у Rust и C++»): `sqrt`, `floor`, `ceil`, `round` от
целого аргумента принимаются без приведения и возвращают `f64`, как в C++
(`std::sqrt(2)` — `double`). `pow` двух целых — целое, как `i32::pow` в Rust,
и ведёт себя как `**`: выход за тип — ошибка выполнения `integer overflow`
(раньше результат молча портился, находка 6 аудита). С дробным аргументом —
`f64`, как `std::pow` в C++. Поведение от дробных аргументов не менялось.

## D-010. `//` — комментарий, деление нацело — `div` (2026-11-12)

Решение владельца по вопросу 1 аудита: `//` всегда начинает комментарий до конца
строки. Раньше `//` после числа, имени или `)` был делением нацело, и
`x = a // комментарий` молча делил. Целочисленное деление с округлением вниз
пишется словом `div` (`-17 div 5` равно `-4`, как `//` в Python и `div` в
Haskell); для беззнаковых — обычное деление. Деление на ноль и
`MIN div -1` — те же ошибки выполнения, что у `/`.

## D-011. Режим в `open` обязателен (2026-11-12)

Решение владельца по вопросу 2 аудита: `open(путь, режим)` — режим обязателен;
`open(путь)` без режима — ошибка компиляции с подсказкой. Раньше режим молча
подставлялся как `"w"`, и `open("data.txt")` для чтения стирал файл.

## D-012. Функция без типа результата — `void` (2026-11-12)

Решение владельца по вопросу 4 аудита («как у Rust и C++»): молчаливого `int`
больше нет. `fn f() { … }` без типа результата ничего не возвращает, как в Rust,
то есть равна `fn void f()`; явные `fn void f()` и `fn int f()` работают, как в
C++. `return значение;` в функции без типа — ошибка компиляции с подсказкой
указать тип. Примеры и тесты с неявным `int` переписаны с явным типом.

## D-013. Имена встроенных функций свободны (2026-11-12)

Решение владельца по вопросу 5 аудита (находка 22): «можно и переменную, и
функцию», как в C++ и Rust. Именем из spec §15 (`max`, `sqrt`, `len` …) можно
назвать свою переменную и свою функцию; своя функция заменяет встроенную во всей
программе. Ключевые слова и имена типов остаются зарезервированными.

## D-014. Строки как в C++ и Rust (2026-11-13, заменяет D-002)

Решения владельца 12.11 и 13.11 (задача 0б). `string` — отдельный тип: неявно в
`ptr` не превращается, руками не освобождается (`del` строки — ошибка).
`replace(s, a, b)` возвращает только `string`; старая запись `ptr r = replace(…)`
+ `del r` — ошибка компиляции с подсказкой, как переписать. Адрес символов
берётся явно функцией, оба имени: `data(s)` (C++) и `as_ptr(s)` (Rust); `&s` для
строки — ошибка. `string b = a` — копия (C++), перенос — словом `move`, после
него старое имя использовать нельзя (Rust). Память строки, в том числе из
`str()`, ввода и `replace`, освобождается сама в конце блока. Шаги — отдельными
PR (журнал — `docs/progress.md`); пока автоосвобождение не слито, такие строки
утекают (spec §17), но не портят память.

Дополнение 13.11: `data(временная строка)` / `as_ptr(…)` (например `data(str(1))`)
— ошибка компиляции: временная строка освобождается в конце оператора, адрес
висел бы. Владелец ответил «твой выбор», оставлен запрет по рекомендации.

## D-015. Перенос строки — `move(имя)` (2026-11-13)

Решение владельца 13.11 («я понял что только перенос со ()»): перенос пишется
только со скобками — `string b = move(a);`, формы `move a` нет (на неё — обычная
синтаксическая ошибка). После `move(a)` имя `a` использовать нельзя (ошибка
компиляции «используется после move», в том числе после ветки, где был перенос);
новое присваивание `a = …` снова делает имя пригодным. Аргумент — имя
string-переменной или параметра; `move` внешней переменной внутри цикла или
функции — ошибка. Память не копируется: в `a` остаётся пустой указатель, конец
блока его не освобождает.

Уточнение владельца 13.11 («Да, если тут же забираешь обратно (как в Rust)»):
`move(имя)` внешней переменной внутри цикла или функции разрешён, если в том же
операторе этому имени присваивается новое значение — `q = enqueue(move(q), i);`,
`s = f(move(s));`. Во всех остальных случаях (`w = f(move(v))`, `T b = move(a);`)
запрет и текст ошибки прежние. Одно правило для строк, структур и растущих
массивов.

## D-016. Структуры с любыми полями, как в C++ и Rust (2026-11-13)

Решения владельца 13.11 (задача 1.2): «сделай так чтобы с любыми полями в с++ как
и в расте» — структуры с полями `string`, `ptr`, динамический массив (и во
вложенных структурах) делаются раньше массива структур; ограничение письма
«владельческие поля ждут 5.2» для полей структур снято. На вопрос о копии
владелец выбрал кнопку «Копия, перенос через move(q)» и подтвердил словами
(«да именно так»):
- строка (и динамический массив) в поле принадлежит структуре и освобождается
  сама, когда структура выходит из области (все выходы из блока), в том числе во
  вложенной структуре;
- `P w = q;`, `w = q;`, передача в функцию по значению — полная копия (C++): у `w`
  свои строки, каждая структура освобождает свои; перенос без копии — только явно
  `P w = move(q);`, после него `q` нельзя использовать до нового присваивания
  (Rust, как D-015);
- поле `ptr` ведёт себя как ptr-переменная: копируется адрес, само ничего не
  освобождается;
- `drop t.scores;` (массив в поле) разрешён раньше срока.
Шаги — отдельными PR (журнал — `docs/progress.md`).

## D-017. Массив в поле структуры (2026-11-13)

Решение владельца 13.11 (продолжение D-016). Поле `T[] имя;` (элементы — числа,
`bool`, `char`) — растущий массив, принадлежит структуре: сначала пустой,
освобождается сам вместе со структурой; копия структуры — полная копия массива,
`move` и `return` — перенос. Владелец выбрал два слова («Да, два слова»):
- `t.scores.clear();` — как `clear()` у вектора в C++: массив пустой (`len()` = 0,
  память остаётся), `push` снова работает, чтение элемента — ошибка выполнения «вне
  границ», повторный `clear` безопасен, структуру можно копировать и передавать.
  `clear()` есть и у динамических массивов-переменных (`v.clear()`).
- `drop t.scores;` — как `drop` в Rust и как `drop` у переменных: память возвращена,
  до нового присваивания `t.scores = [...]` поле нельзя читать и менять (`push`,
  `len`, индекс, `clear`), всю `t` нельзя копировать, передавать, возвращать и
  переносить; повторный `drop` — ошибка компиляции; в конце области поле второй раз
  не освобождается. `drop` поля внешней структуры внутри цикла или функции —
  ошибка (как у переменных).
Массивы-переменные пока остаются с ручным `drop`;
это расхождение снимается в задаче 1.3 (D-018).

## D-018. Растущий массив-переменная: копия, перенос, автоосвобождение (2026-11-13)

Решение владельца 13.11 (ответ на вопрос задачи 1.3, одно правило со строками D-015
и структурами D-016):
- Растущий массив, отданный функции, — **копия**, массив вызывающего цел (как
  `vector` в C++). Отдать насовсем — `move(a)`; после этого имя нельзя использовать
  до нового присваивания (как в Rust). Так же `int[] b = a;` — копия,
  `int[] b = move(a);` — перенос.
- Память массива-переменной возвращается **сама в конце блока** (C++ и Rust здесь
  совпадают), как у массива в поле структуры (D-017). `drop v;` раньше конца блока
  разрешён, `del v;` для него делает то же, `clear()` остаётся.
- Локальный массив из функции возвращается без копии (как структуры, PR #116).
- Запись: параметр и результат функции — как поле, `fn int sum(int[] v)`,
  `fn int[] make()`; обычный массив `[1, 2, 3]` в такую функцию отдаётся копией
  (согласовано 13.11).
- Срезы — «Оба способа» (кнопка владельца 13.11): `v[1..4]` как в Rust (конец не
  входит, как в `for i in 0..3`) и `slice(v, 1, 3)` как в C++ (начало и количество);
  оба дают одно окно на часть массива без копии: функция читает и меняет только
  этот кусок, массив остаётся у хозяина, выход за края окна — ошибка; хранить окно
  дольше массива нельзя (время жизни — 5.2).
- Параметр-окно (владелец 13.11: «это мы же говорили» — то же «оба способа»): две
  записи одного типа, `fn int sum(int[..] part)` и `fn int sum(slice int[] part)`;
  `span<int>` нет. Весь массив в такой параметр отдаётся без копии (`sum(v)`, как
  `&v` в Rust и `span` из `vector` в C++; решено ведущим 13.11).
- Сделано (1.3, шаг 5): окно — только параметр функции; срез в переменной — ошибка
  компиляции до 5.2. В окне нельзя менять длину (`push/pop/resize/clear`), `drop`,
  `move` и присваивание окну; `int[] c = part` и `return part` — копия. Срез за
  краями — ошибка выполнения `slice out of bounds`; если в программе есть своя
  функция `slice`, `slice(…)` вызывает её (срез — `v[a..b]`).

## D-019. Строки: байт по номеру и буквы по очереди (2026-11-13)

- Владелец 13.11 (форма, 1.1): «оба» — байт по номеру (как в C++) и буквы по
  очереди (как в Rust), с явным различием байта и буквы.
- Сделано (1.1, первый PR): `s[i]` — байт `u8`, номер от `0` до `len(s) - 1`,

  ошибка компиляции (менять байт — через `data(s)`); сравнение с переменной
  `char` — через `(u8) c` (байт и буква различаются явно). Обход по буквам — следующими PR.

## D-020. Строки: сравнения < > <= >= (2026-11-13)

- Строки сравниваются всеми шестью операциями по содержимому, байт за байтом,
  байты — без знака (`strcmp`): как `std::string::compare` в C++ и `Ord` для
  `String` в Rust — оба языка согласны, решено без вопроса владельцу.
  Более короткое начало меньше (`"ab" < "abc"`). Строка с числом — ошибка компиляции.

## D-021. char — буква Юникода, 32 бита (2026-11-13)

- Владелец 13.11 (16:38): «Букву char, как в Rust». `char` — номер буквы Юникода
  (`0..0x10FFFF` без суррогатов), в памяти 32 бита; байт — `u8`/`byte`. Литерал
  `'é'` — одна буква; `print` печатает её в UTF-8. `(char) n` с не-номером буквы —
  ошибка выполнения `invalid char` (как `char::from_u32` в Rust). `char` → `u8` — с
  проверкой (≤ 255). `data(s)` — указатель на байты `u8` (раньше «на char»), `p[i]`
  печатается числом, как `s[i]`. Байт сравнивается только с буквой ASCII.
- Общий принцип владельца (13.11, о `s[i]`): «пишется коротко как в C++, а ведёт себя
  безопасно как в Rust» — так решать и советовать и дальше.
- Запись `s[i] = …` (владелец 13.11, 16:41): «запрет, но с отдельным явным способом» —
  остаётся ошибкой компиляции с подсказкой; менять байты — только через `data(s)`.
- Обход строки по буквам (`letters(s)`) даёт `char` — D-022.

## D-022. Обход строки по буквам: for c in letters(s) (2026-11-13)

- `for c in letters(s)` — буквы строки по очереди, `c` — `char` (D-021; как
  `s.chars()` в Rust). `len(s)` по-прежнему считает байты.
- Байт не из UTF-8 (обрыв, лишний байт продолжения, суррогат, слишком длинная
  запись) даёт U+FFFD — по одной на каждый неверный байт. Это проще, чем
  «maximal subpart» в `String::from_utf8_lossy` Rust (там `\xe2\x82` — одна U+FFFD),
  зато без чтения за концом строки; правильный UTF-8 обходится одинаково.
- В скобках — только имя строки (переменная или параметр): поле и временная строка —
  позже (как `for x in v`, шаг 6 плана). Присваивать этой строке внутри цикла —
  ошибка компиляции, как менять длину `v` в `for x in v`.
