# SC Core Audit — Техническая карта текущего состояния компилятора

*Автоматически сгенерировано на основе анализа исходного кода репозитория*

---

## 1. Общая архитектура

### Pipeline
```
Lexer (lexer.cpp/h) → Parser (parser.cpp/h) → AST (Node) → 
Semantic Analysis (semantic.cpp) → Type Checking (в semantic.cpp) → 
LLVM Codegen (codegen.cpp/h) → LLVM Verification → Executable
```

### Ключевые файлы
| Файл | Строк | Назначение |
|---|---:|---|
| `lexer.cpp/h` | ~22K | Лексический анализ, токены |
| `parser.cpp/h` | ~40K | Рекурсивный спуск, AST |
| `semantic.cpp` | ~53K | Символьные таблицы, проверка типов, definite assignment |
| `codegen.cpp/h` | ~80K | LLVM IR генерация |
| `main.cpp` | ~4K | CLI, orchestration |
| `test.sh` | ~34K | Полный тестовый набор |

## 2. Аудит по подсистемам

### 2.1 Система типов

| Подсистема | Текущее состояние | Проблемы | Что необходимо сделать |
|---|---|---|---|
| **Базовые типы** | `i8,i16,i32,i64,u8,u16,u32,u64,f32,f64,byte,short,ushort,int,uint,long,ulong,float,double,bool,char,str,ptr,rox(void)` | Нет единого внутреннего представления `Type`/`TypeId`; типы сравниваются строками; нормализация в `semantic.cpp::normalize()` | Ввести `struct Type` с `Kind`, `size`, `signedness`, `llvmType`, централизованные операции |
| **Проверка до LLVM** | Семантический анализ проверяет типы выражений, присваиваний, вызовов | Частично: некоторые случаи пропускаются (например, неявные сужения в арифметике) | Полная проверка всех выражений до codegen; ошибки типов не должны доходить до LLVM |
| **Скрытые преобразования** | `castTo()` в codegen делает неявные расширения/сужения | Неявные сужения `i64→i32`, `f64→f32`, `signed→unsigned` без диагностики | Таблица разрешённых неявных преобразований; остальные — только явный `cast` |
| **LLVM fallback** | `svType()` возвращает `i32` для неизвестных типов | Маскирует ошибки типов | Убрать fallback; неизвестный тип = ошибка семантики |

**Вывод:** Система типов работает на строковом сопоставлении, не единообразна, позволяет неявные потери данных.

### 2.2 Массивы

| Подсистема | Текущее состояние | Проблемы | Что необходимо сделать |
|---|---|---|---|
| **Статические массивы** | `type name[n] = {…}`; `NODE_ARRAY_DECL` | Проверка границ есть (runtime), но нет compile-time для констант; инициализаторы не проверяются на длину; элементы не проверяются на совместимость типов строго | Compile-time bounds для констант; строгая проверка инициализаторов; диагностика излишних/недостающих элементов |
| **Динамические массивы** | `ptr name = nw type[n]` (`NODE_DYN_ARRAY`); дескриптор `{ptr data; i64 len; i64 cap}` в codegen; runtime bounds check ✅ | Семантика возвращает `ptr`, теряется информация о типе элемента в Symbol; нет операций `push`, `pop`, `resize`, `len()`, `cap()`; нет slice/view | Полная семантика: методы/операции; `len`/`cap` свойства; slice type; ownership модель |
| **Проверка границ** | Runtime через `emitArrayBoundsCheck` для статических и динамических | Ошибка вызывает `exit(1)` через `puts`+`abort`; нет единого механизма ошибок; нет проверки отрицательных для unsigned индексов | Единый `bounds_check` с понятным сообщением; опционально — `panic`/`result` модель |
| **Срезы (slices)** | ❌ Отсутствуют | — | Проектировать после модели памяти |

**Вывод:** Динамические массивы имеют runtime metadata и bounds check — хорошо. Статические нуждаются в compile-time проверках. Нет slices, нет высокоуровневых операций.

### 2.3 Структуры

| Подсистема | Текущее состояние | Проблемы | Что необходимо сделать |
|---|---|---|---|
| **Объявление** | `rec Name { field: type; … }` (`NODE_STRUCT_DEF`) | Порядок полей сохраняется; layout делегирован LLVM; нет проверки рекурсивных определений по значению | Добавить проверку цикличности; задокументировать layout правила |
| **Инициализация** | `rec Name { field: value, … }` (`NODE_STRUCT_INIT`) | Проверка полей есть; нет проверки отсутствующих обязательных полей; нет default values | Полная валидация инициализатора |
| **Доступ к полям** | `expr.field` (`NODE_FIELD_ACCESS`) | Проверка типа/существования есть | ✅ Работает |
| **Вложенность** | Поддерживается через рекурсивные `svType` | Нет проверки бесконечного размера | Добавить проверку |
| **Копирование/перемещение** | `memcpy` через LLVM `load`/`store` | Поверхностное копирование; нет ownership семантики; двойное освобождение возможно для полей-указателей | Определить модель: `Copy`/`Move`/`Clone` traits или запрет неявного копирования для owning типов |

**Вывод:** Базовая работа есть, но нет модели владения, нет безопасности копирования.

### 2.4 Функции

| Подсистема | Текущее состояние | Проблемы | Что необходимо сделать |
|---|---|---|---|
| **Объявление** | `fn name(params) -> ret { … }` | Параметры: `name:type`; проверка арности и типов есть | ✅ База работает |
| **Возврат значений** | `ret expr` | Return analysis: проверяет все пути (`checkFunction` → `checkAllPathsReturn`) | ✅ Работает (Stage 3) |
| **Вызов** | `name(args)` | Проверка типов аргументов есть; нет проверки перегрузки (пока не нужна) | ✅ База работает |
| **Forward declarations** | `fn int name(type arg);` | — | ✅ Реализовано: распознавание, валидация соответствия (тип результата, арность, типы параметров), отклонение дубликатов |
| **Передача больших объектов** | По значению через `alloca` + `memcpy` | Неявное копирование структур/массивов; нет `ref`/`mut ref`/`owned` семантики | Ввести режимы передачи после модели памяти |

**Вывод:** Функции работают корректно для простых случаев. Нужен control-flow return analysis (есть), но нет режимов передачи.

### 2.5 Память и владение

| Подсистема | Текущее состояние | Проблемы | Что необходимо сделать |
|---|---|---|---|
| **Модель** | ❌ Нет явной модели | `malloc`/`free` для dyn arrays; `alloca` для локальных; нет ownership/borrowing | **Критично:** спроектировать и реализовать минимальную ownership модель |
| **Стек/куча** | Неявно: локальные — стек, `nw` — куча | Нет правил для возврата указателей на стек; нет escape analysis | Escape analysis или запрет возврата `ptr` на локальные |
| **Инициализация** | Definite assignment для скаляров/массивов/параметров ✅ | Нет для полей структур, нет для элементов массива при частичной инициализации | Расширить definite assignment |
| **Освобождение** | `del` для dyn arrays (`free(data)`) | Нет деструкторов; нет RAII; нет drop order | Ввести `drop`/`defer` или деструкторы |
| **Утечки** | LeakSanitizer чист для тестов | Нет статического анализа утечек | Опционально: интеграция с ASan |

**Вывод:** Модели памяти нет — это главная архитектурная дыра.

## 4. Что работает частично / с ограничениями ⚠️

1. **Система типов** — строковое сравнение, неявные сужения, нет единого `Type`
2. **Статические массивы** — нет compile-time bounds check для констант
3. **Динамические массивы** — нет `push/pop/resize/len/cap`, нет slices
4. **Структуры** — нет ownership/copy semantics, нет проверки рекурсивного размера
5. **Функции** — нет режимов передачи (by ref/mut/owned)
6. **Память** — нет модели владения, нет RAII, нет деструкторов
7. **Преобразования типов** — неявные сужения без диагностики
8. **Арифметика** — нет checked overflow, нет wrapping/saturating API
